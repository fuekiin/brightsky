# Fork management: brightsky + dwdparse

We run **two forks** that together form one feature. The parsing logic lives in dwdparse, the
service wrapping (exporter, migration, query, web) in brightsky. Most changes touch both.

## Repos, remotes, branches

```
<parent>/
  brightsky/   ← github.com/fuekiin/brightsky   (origin), jdemaeyer/brightsky (upstream)
  dwdparse/    ← github.com/fuekiin/dwdparse    (origin), jdemaeyer/dwdparse  (upstream)
```

Branch model, identical in both repos:

- `master` — tracks `upstream/master`, never carries our commits.
- `nano-health` — our feature/deploy branch, rebased onto `upstream/master`.

(2026-07-13: dwdparse's `upstream` remote wrongly pointed at our own fork; fixed with
`git remote set-url upstream git@github.com:jdemaeyer/dwdparse.git`.)

## Rebase workflow

```bash
git fetch upstream
git checkout master && git merge --ff-only upstream/master
git checkout nano-health && git rebase master
# run the tests, then force-push the feature branch
git push --force-with-lease origin nano-health
```

Do brightsky and dwdparse independently; they don't need to be rebased in lockstep. Our changes
are deliberately **additive** (appended classes, new files, one-line registry entries), so
rebases should apply cleanly; if a rebase conflicts on something upstream restructured, prefer
re-appending our code in the new shape over fighting the diff.

## The coupling point: how brightsky depends on dwdparse

- `pyproject.toml` lists `dwdparse[all]` (unversioned) — we leave this untouched.
- `requirements.txt` is the deploy lockfile. Upstream pins `dwdparse==0.9.22` (PyPI); **our fork
  pins a git ref of our dwdparse fork instead**:

  ```
  dwdparse @ git+https://github.com/fuekiin/dwdparse.git@<commit-sha>
  ```

  Always a **commit SHA or tag, never a branch name** — branches move, deploys must not.
- For local development, install the sibling checkout editable **after** the requirements:
  `pip install -e ../dwdparse` (or the `uv pip install ... -e ../dwdparse -e .` one-liner in
  [README.md](README.md)). The editable install shadows the pinned one.

### Build order when the parser changes

1. Commit in `../dwdparse` on `nano-health`; run its tests.
2. `git push origin nano-health` in dwdparse (the SHA must be public before it can be pinned —
   a pin referencing an unpushed SHA breaks every non-local install).
3. Update the SHA in brightsky's `requirements.txt` **and `requirements-dev.txt`** (CI installs
   only the dev file — a stale pin there makes CI test against PyPI dwdparse).
4. Commit brightsky (parser pin + whatever service change accompanies it); run tests; push.
   The `nano CI` workflow then builds and pushes the deployable image to GHCR.

Note that `requirements.txt` is generated by `uv pip compile` upstream. When upstream's
regenerated file conflicts on rebase, take upstream's version and re-apply our single
`dwdparse @ git+...` line.

## Upstreaming and the exit plan

The dwdparse fork exists only to host parsers upstream doesn't have yet. The parser code is
written "upstream-shaped" (stdlib only, follows the existing class patterns, no
brightsky-specific logic) precisely so it can be offered to `jdemaeyer/dwdparse` as a PR.

If/when `PollenParser` (and later siblings) are merged upstream and released:

1. Switch brightsky's `requirements.txt` back to a PyPI pin (`dwdparse==<version>` with the
   feature included).
2. Drop our dwdparse commits: `git checkout nano-health && git rebase upstream/master` — our
   commits should reduce to no-ops/conflicts that resolve to upstream's version; or simply
   delete the `nano-health` branch and the fork.
3. brightsky-side code (exporter, migration, endpoint) is unaffected — it only imports
   `dwdparse.parsers.PollenParser`, wherever it comes from.

The brightsky fork we keep long-term either way (upstream may or may not want a `/pollen`
endpoint; that's a separate conversation).
